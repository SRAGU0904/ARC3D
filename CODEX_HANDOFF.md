## Design Goal

The original goal was to make a 3D demo inspired by ARC1 task `543a7ed5`, extending 2D ARC-style reasoning into voxel puzzles while keeping the spirit of pattern abstraction.

The demo should be visually simple and usable by humans and models:

- no long intro text
- no 2D examples on the main page
- 3D workspace is the main focus
- task layout is consistent across Task 1, Task 2, and Task 3
- users should answer through the answer buttons, not by clicking cubes directly
- candidate labels are attached to cube faces, not floating icons

## Task 2

Task 2 is a nearest-cube / spatial distance puzzle.

Current concept:

- A manually defined broken rectangular voxel body is placed inside the workspace.
- A separate blue unit cube is placed at some distance from the broken/slanted surface.

## Camera Modes

There are two camera modes:

- Fixed view
- Free view

The mode toggle appears in the 3D workspace. Free view uses `TrackballControls`, allowing free rotation including upside-down viewing.

Fixed view uses discrete camera navigation.

## Fixed Camera Logic

The fixed camera is implemented as a 26-view system:

- 6 face views
- 12 edge views
- 8 vertex views

The important state variables are:

```js
let currentViewId = ...
let currentCameraDirection = ...
let currentCameraUp = ...
let cameraTarget = ...
```

Meaning:

- `currentViewId`: the current named discrete view, such as `x- y+ z+`
- `currentCameraDirection`: the camera direction vector
- `currentCameraUp`: the head/up direction of the camera
- `cameraTarget`: the center of the voxel structure, used to keep the object visually centered

Core function:

```js
function getNextView(move) { ... }
```

Location:

```text
task1/main.js
task2/main.js
task3/main.js
```

The three versions should remain synchronized.

Current fixed-view behavior:

- `left` / `right`: rotate the camera direction by 45 degrees around the current head/up axis.
- `up` / `down`: rotate the camera direction and head/up direction by 45 degrees around the current screen-right axis.
- vertex views: only `left` and `right` are allowed.
- face and edge views: `left`, `right`, `up`, and `down` are allowed.
- after each move, the camera direction snaps to a standard discrete face/edge/vertex direction.

Important helper functions:

```js
getNextView(move)
setView(nextView)
resetCamera()
screenRightVector(viewVector, upVector)
snapVectorToDirection(vector)
snapCameraUp(upVector, viewDir, fallback)
isCurrentVertexView()
```

## Recent Camera Issue History

There was repeated debugging around vertex views.

Problem:

- Earlier versions kept continuous camera vectors after 45-degree rotations.
- The UI label might say the view was a vertex, but the real camera direction was still a continuous vector.
- This caused follow-up rotations from vertex states to feel wrong.

Current fix:

- After each fixed-view move, `direction` is reset to `viewDirection(nextDir)`.
- This forces the camera into a true discrete face/edge/vertex direction.
- Vertex detection now checks the snapped camera direction rather than relying only on the string `currentViewId`.

Relevant current code shape:

```js
const nextDirection = rotateVector(directionVector, upVector, angle);
const nextDir = snapVectorToDirection(nextDirection);

return {
  viewId: viewIdForDirection(nextDir),
  direction: viewDirection(nextDir),
  upVector,
};
```

## Styling Notes

General UI preferences:

- No outer transparent large cube/cage.
- Voxels should touch each other without gaps.
- Black lines separate voxel faces.
- Empty/missing cube positions should have no color or placeholder marker.
- The 3D canvas should be compact enough to avoid page scrolling.
- Main workspace should remain visually centered.

If cube grid lines disappear at some angles:

- check material `polygonOffset`
- check edge line rendering
- check depth conflict between cube faces, label planes, and edge lines
